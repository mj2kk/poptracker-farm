# PopTracker Farm · Этап 3A: Android UI Automation Engine

**Статус:** техническое задание для Codex  
**Дата:** 19 ноября 2026  
**Цель:** научить зарегистрированный Android Agent выполнять ограниченные, проверяемые действия в интерфейсе собственного тестового Android-приложения без USB, ADB и Mac во время исполнения.

## 1. Исходная точка и границы

Этап 2 завершён на **OPPO CPH2197 / Android 13 / API 33**, агент **0.2.1**. По отчёту пользователя агент сохранил регистрацию и выполнил `PING`, `GET_DEVICE_STATUS`, `EXECUTE_TEST_TASK`; финальная проверка повторной доставки результата после обрыва HTTPS прошла. Подтверждены 47 серверных и 10 Android-тестов. Три телефона одновременно и работа с выключенным экраном **не проверены**.

Фактический проект на VPS: `/PopTracker Farm`; отдельный PHP 8.3/PDO API, MySQL `poptracker_farm`, HTTPS `https://7s-01d.online/api/device/v1/`. **Это не Laravel-сервис**. Не изменять существующий PopTracker в `/var/www/projects/dataroom-agents-lab`, TikTok-парсер, его БД и расписания.

Перед изменениями Codex должен прочитать актуальные исходники, `PROJECT.md`, `docs/setup.md`, отчёты этапов 1–2 и проверить фактическую реализацию API, задач, lease и локального outbox. Если фактический код отличается от этого ТЗ, зафиксировать расхождения и адаптировать план, не ломая действующие функции.

## 2. Что входит в этап

1. В Android Agent добавить **AccessibilityService** с явным ручным включением в системных настройках.
2. Добавить **собственный тестовый экран** внутри Agent APK с детерминированными элементами интерфейса: кнопка, счётчик, прокручиваемый список и текстовый индикатор результата.
3. Добавить **строго типизированное** серверное задание `UI_TEST_SCENARIO` с фиксированным сценарием и схемой ответа.
4. На OPPO выполнить удалённый сценарий через AccessibilityService, получить структурированный результат и диагностический отчёт.
5. Сохранить регистрацию, heartbeat и все три типа задач этапа 2.

**Не входит:** TikTok, извлечение данных из сторонних приложений, обход ограничений приложений, перехват трафика, OCR, MediaProjection, root, ADB по сети, произвольные жесты по команде сервера, shell/скрипты, удалённая установка APK, фоновая работа с заблокированным экраном, панель управления и подключение всех трёх телефонов.

## 3. Принцип безопасности

AccessibilityService обладает широкими возможностями. Использовать его **исключительно в пределах собственного пакета Agent** на этом этапе. Проверять `packageName` активного окна и каждого целевого узла перед действием. Любой другой пакет → остановить сценарий с кодом `TARGET_PACKAGE_MISMATCH` без попытки продолжения. Никаких универсальных команд вида `tap(x,y)`, `swipe`, `type_text`, `open_app(package)` через серверный API. Не собирать содержимое чужих окон, пароли, уведомления, персональные данные или полный дамп дерева UI.

В UI агента явно показывать, включён ли AccessibilityService; объяснять пользователю, зачем разрешение нужно и как его отключить. Не пытаться включать службу программно. Проверить применимость правил Android и, если планируется публикация через Google Play, отдельно оценить политику Accessibility API; публикация не является целью этого этапа.

## 4. Тестовый экран

Создать экран `Automation Test` в существующем Android-приложении. Он должен содержать:

- Кнопку с постоянным resource ID `test_increment_button`.
- Счётчик `test_counter_value`, начальное значение 0 и инкремент по нажатию.
- Прокручиваемый список с не менее чем 30 строками, каждая с устойчивым ID/доступным текстом, включая элемент `Test Item 25`.
- Индикатор `test_scenario_status` со значениями `IDLE`, `RUNNING`, `PASSED`, `FAILED`.
- Кнопку ручного сброса состояния теста.

Реализовать доступную семантику UI для Accessibility (важно при Jetpack Compose). Не привязываться к абсолютным координатам, разрешению, плотности экрана или локализации.

## 5. Сценарий UI_TEST_SCENARIO v1

Сервер принимает только:

```json
{
  "type": "UI_TEST_SCENARIO",
  "schema_version": 1,
  "parameters": {"scenario": "OWN_APP_BUTTON_AND_SCROLL_V1"}
}
```

Агент должен:

1. Проверить, что разрешение AccessibilityService активно; если нет, вернуть `ACCESSIBILITY_DISABLED` (не запускать настройки без действия пользователя).
2. Проверить, что приложение находится на собственном тестовом экране; при необходимости показать пользователю инструкцию открыть его вручную. Не переключать приложения скрытно.
3. Сбросить тестовый счётчик в 0 штатным механизмом собственного экрана; зафиксировать стартовое состояние.
4. Через AccessibilityService найти кнопку по устойчивому идентификатору/семантике и вызвать `ACTION_CLICK`.
5. Через Accessibility прочитать значение счётчика и подтвердить `1`.
6. Прокрутить **собственный** список с помощью поддерживаемого accessibility action, найти `Test Item 25`, проверить его доступность.
7. Завершить `PASSED`, только если все проверки выполнены. Иначе вернуть конкретную ошибку, шаг и диагностические сведения.

Предусмотреть таймаут на каждый шаг (например, 5 секунд) и общий ограниченный таймаут (например, 30 секунд). Исполнение должно быть последовательным, отменяемым и не блокировать главный UI-поток. Повторное исполнение должно начинаться со сброса состояния, чтобы результат был воспроизводимым.

## 6. Результат и протокол

Предлагаемая схема ответа (уточнить под фактический протокол этапа 2):

```json
{
  "schema_version": 1,
  "scenario": "OWN_APP_BUTTON_AND_SCROLL_V1",
  "status": "PASSED",
  "steps": [
    {"name": "permission_check", "status": "PASSED", "duration_ms": 10},
    {"name": "button_click", "status": "PASSED", "duration_ms": 120},
    {"name": "counter_verify", "status": "PASSED", "observed_value": "1"},
    {"name": "scroll_find_item", "status": "PASSED", "observed_value": "Test Item 25"}
  ],
  "duration_ms": 1500,
  "error_code": null
}
```

Пример иллюстративный, не выдавать значения времени за результаты теста. При ошибке `status=FAILED`, `error_code` из ограниченного набора (`ACCESSIBILITY_DISABLED`, `TEST_SCREEN_NOT_OPEN`, `TARGET_PACKAGE_MISMATCH`, `NODE_NOT_FOUND`, `ACTION_FAILED`, `STEP_TIMEOUT`, `SCENARIO_TIMEOUT`, `CANCELLED`, `INTERNAL_ERROR`). Не отправлять полный текст чужих экранов или чувствительные данные.

Сохранить существующую модель `task_id` / `attempt_id`, дедупликацию и локальное хранение результата до доставки. Не превращать повторную доставку результата в повторное выполнение UI-сценария. **Отдельно проверить** случай, когда результат готов, но сеть недоступна дольше 120-секундного lease: зафиксировать фактическое поведение и предложить безопасную коррекцию протокола, если она необходима. Не маскировать проблему уменьшением интервала retry.

## 7. Серверные изменения

- Добавить `UI_TEST_SCENARIO` в строгий allowlist типов заданий, с серверной валидацией схемы и значения `scenario`.
- Не добавлять произвольный JSON-план действий, URL, имена пакетов, координаты или команды ОС.
- Сохранить обратную совместимость трёх заданий этапа 2 и старого агента: неподдерживаемый тип не должен назначаться несовместимой версии клиента.
- Добавить минимальное указание capabilities/версии агента, если такого механизма ещё нет; сервер должен знать, поддерживает ли устройство `UI_TEST_SCENARIO`.
- CLI: создавать, просматривать и отменять задание существующими командами `task:create`, `task:show`, `task:cancel`, по возможности без новых интерфейсов.
- Миграции выполнять только при реальной необходимости. Перед деплоем: backup файлов и согласованная резервная копия БД; описать rollback.

## 8. Android-реализация

- Kotlin, существующая сборочная система и подпись APK; **не терять действующую регистрацию** при `install -r`.
- AccessibilityService описать в Manifest и отдельном XML-конфиге с минимально необходимыми флагами; не запрашивать `canRetrieveWindowContent` шире, чем требуется, и не включать ненужные возможности.
- Разделить `AutomationTestScreen`, `OwnAppAccessibilityService`, `UiTestScenarioRunner`, `UiTestResult` (имена примерные).
- Не полагаться на один глобальный `AccessibilityNodeInfo` между событиями: обновлять/переискать узлы, корректно обрабатывать их исчезновение.
- Исключить гонки: одновременно только один UI-сценарий на устройство; при закрытии тестового экрана или выключении службы сценарий завершается понятной ошибкой.
- Предусмотреть локальную индикацию выполняемого теста и понятную возможность остановить его.

## 9. Порядок работы Codex

1. **Аудит:** прочитать реальный проект, подтвердить расположение исходников и тестов, версию APK и структуру задач. Зафиксировать ограничения API 33.
2. **План:** перечислить файлы и совместимость, выбрать минимальные изменения; не рефакторить посторонние части.
3. **Реализация:** собственный тестовый экран → AccessibilityService → сценарий → серверный allowlist → отчёт.
4. **Автотесты:** Kotlin unit/instrumented tests для схем, состояния, ошибок; PHP тесты в отдельной тестовой БД для валидации типа, авторизации, идемпотентности и несовместимых клиентов.
5. **Развёртывание:** резервные копии, тесты, сборка APK, установка на OPPO с сохранением подписи и токена; не трогать production PopTracker.
6. **Физический E2E:** отключить USB, выполнить задачу с VPS, убедиться в результате на сервере и в приложении. Если телефон недоступен, честно отметить отсутствие E2E.
7. **Отчёт:** `docs/step-03a-report.md` с версиями, командами, фактическими результатами, ограничениями, временем событий и откатом; обновить `docs/setup.md`.

## 10. Обязательные проверки

| Проверка | Ожидаемый результат |
|---|---|
| Accessibility выключен | Явная ошибка, никаких скрытых действий |
| Разрешение включено, открыт тестовый экран | Сценарий проходит, счётчик = 1, найден Item 25 |
| Открыт другой экран/приложение | Безопасный отказ без взаимодействия с ним |
| Пропал целевой UI-узел | Контролируемый `NODE_NOT_FOUND`/timeout |
| Повторная доставка результата | Одна итоговая запись, без повторного клика |
| Два задания UI одновременно | Строго последовательное исполнение или отказ второго |
| Сеть пропала после исполнения | Результат сохраняется локально и доставляется при восстановлении в рамках фактической серверной политики |
| Старые PING/STATUS/TEST_TASK | Работают без регрессии |
| Обновление APK | Регистрация устройства сохранена |
| Нет USB во время исполнения | Команда и результат проходят через VPS |

## 11. Критерии приёмки

Этап 3A завершён **только если** на реальном OPPO без USB: оператор создаёт `UI_TEST_SCENARIO` на VPS; агент с вручную включённым AccessibilityService и открытым собственным тестовым экраном получает задачу; через AccessibilityService нажимает кнопку, проверяет счётчик, прокручивает список, находит Item 25; отправляет структурированный результат; сервер показывает один корректный итог. Отдельно должны пройти негативные проверки разрешения, чужого окна, таймаутов и регрессионные тесты этапа 2.

Если инструментальные тесты пройдены, но физический E2E не выполнен, статус **«реализация готова, физическая приёмка не пройдена»**.
