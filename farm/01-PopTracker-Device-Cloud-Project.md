# PopTracker Device Cloud

## 1. Назначение

Создать централизованную систему управления парком Android-устройств для PopTracker. Устройства должны выполнять задания по сбору доступных данных TikTok независимо от USB-подключения к Mac, а сервер должен распределять задачи, принимать результаты и отображать состояние устройств.

**Основной принцип:** Android инициирует исходящее соединение с сервером. Постоянное подключение Mac и доступ сервера к ADB не требуются.

## 2. Исходная ситуация

- Есть три физических Android-устройства и работающий процесс сбора TikTok через Mac, USB и скрипты, которые сопровождает Codex.
- Есть сервер Ubuntu и существующий проект PopTracker с MySQL.
- Существующая БД включает `poptracker_authors`, `poptracker_videos`, `poptracker_observations`, `poptracker_scans`, `poptracker_comments`, `poptracker_author_geo_evidence`.
- Точные версии Android, текущий способ извлечения данных и структура репозитория требуют инвентаризации. Не считать их известными заранее.

## 3. Целевое поведение

1. На каждый Android устанавливается собственный **PopTracker Agent APK**.
2. Агент проходит регистрацию на Control Server по HTTPS и хранит индивидуальные учётные данные безопасно.
3. Агент сообщает о состоянии, получает задания и передаёт результаты через API; при необходимости позже добавляется WebSocket.
4. Сервер отслеживает доступность, выдаёт задания с lease, принимает идемпотентные результаты и хранит диагностику.
5. Сбой одного устройства не останавливает остальные; после потери сети агент переподключается.
6. Codex помогает разрабатывать и диагностировать систему, но выполнение заданий не зависит от постоянно работающего Codex.

## 4. Компоненты

### Android Agent

- Kotlin, нативное Android-приложение; простой UI состояния.
- Модуль регистрации и авторизации устройства.
- Менеджер соединения с тайм-аутами и повторными попытками.
- Локальное хранение конфигурации и очереди неподтверждённых сообщений.
- Исполнитель ограниченного набора типизированных задач; произвольное выполнение shell-команд с сервера запрещено.
- Позднее: интеграция с Android Accessibility API или иными разрешёнными механизмами автоматизации, после отдельного исследования и проверки на устройствах.

### Control Server

- Предпочтительно Laravel + MySQL, если это соответствует существующему проекту.
- HTTPS API регистрации, heartbeat, задач и событий.
- Отдельные таблицы управления устройствами, не нарушающие существующие таблицы PopTracker.
- Позднее: очередь, UI мониторинга, аудит действий и управление версиями.

### Data pipeline

- Агенты не получают прямого доступа к MySQL.
- Сервер валидирует и дедуплицирует данные по стабильным идентификаторам.
- Существующие таблицы видео и наблюдений остаются источником аналитики; изменения схемы планируются отдельно.

## 5. Этапы

| Этап | Результат | Критерий приёмки |
|---|---|---|
| 1. Connectivity MVP | APK + Control API + регистрация + heartbeat | Один Android виден на сервере без USB и Mac; после временной потери сети восстанавливает связь |
| 2. Task execution | Типизированные задания, статусы и результаты | Три устройства независимо выполняют тестовые задания |
| 3. Automation adapter | Перенос одного проверенного сценария существующего парсера | Одно устройство выполняет сценарий автономно в рамках доступных Android API |
| 4. Distributed collection | Параллельная работа, checkpoint, диагностика | Три устройства работают параллельно, сбои изолированы |
| 5. Operations | Панель управления, обновления, метрики | Оператор наблюдает парк и управляет безопасным выпуском версий |

## 6. Нефункциональные требования

- **Безопасность:** TLS, уникальные токены устройств, возможность отзыва, секреты вне репозитория, серверная валидация входящих данных, минимальные Android-разрешения, ограничение частоты запросов, аудит.
- **Надёжность:** тайм-ауты, backoff с jitter, идемпотентность, диагностика, отсутствие потери подтверждённых данных, защита от повторного исполнения.
- **Масштабирование:** архитектура рассчитана на добавление устройств, но производительность на 10–100 устройств не заявляется без нагрузочных тестов.
- **Android:** учитывать ограничения фонового исполнения, Doze, энергосбережения и перезапусков; не обещать постоянную доступность без проверки на конкретных моделях.
- **Правовые/платформенные рамки:** учитывать условия TikTok, права на данные и приватность; не реализовывать обход защит, ограничений доступа или антибот-механизмов.

## 7. Границы MVP

Первый этап **не включает** парсинг TikTok, AccessibilityService, MediaProjection, WebSocket, удалённое выполнение команд, автообновление APK, Redis, сложную админку и массовое развёртывание. Задача первого этапа: доказать устойчивую двустороннюю связность через исходящие HTTPS-запросы с реального Android.

## 8. Решения, которые нужно подтвердить

- Репозиторий и точка интеграции Laravel.
- Домен сервера и корректный HTTPS-сертификат.
- Минимальная поддерживаемая версия Android по фактическим устройствам.
- Способ установки APK и первоначальной регистрации.
- Способ будущего переноса существующего ADB-парсера после изучения его реализации.

## 9. Принцип разработки

Работать небольшими проверяемыми изменениями. Не ломать действующий сбор PopTracker. Для каждого этапа вести журнал решений, команд проверки, результатов и известных ограничений. Не выдавать успешную сборку APK за доказательство стабильной работы на устройстве.
