# PopTracker Farm · Этап 3B.1: исследование интерфейса TikTok и подготовка миграции парсера

**Статус:** техническое задание для Codex  
**Дата:** 19 ноября 2026  
**Результат:** воспроизводимый отчёт о доступных данных и ограничениях Android Agent, без массового сбора и без переноса парсера в production.

## 1. Контекст

По результатам этапа 3A агент **0.3.1** на **OPPO CPH2197 / Android 13 / API 33** успешно выполнил два последовательных сценария `UI_TEST_SCENARIO` без USB: сброс счётчика, нажатие, чтение значения и прокрутка до `Test Item 25` (590 и 568 мс). Повторная отправка готового отчёта не создала дублирующую завершённую попытку. Проверены отказы при выключенной AccessibilityService, чужом окне и отсутствии кнопки. Серверные проверки: 61; JVM-тесты: 16. **Это подтверждает управление собственным экраном, но не TikTok.**

Известная проблема: после недоступности приёма отчёта в течение 130 секунд сервер отклоняет результат как `409 lease_expired` при 120-секундном lease. Сокращение задержки повторной отправки не решает проблему долгого отключения сети.

Фактическая инфраструктура из предыдущих отчётов: VPS Vuka, `/PopTracker Farm`, отдельный PHP/PDO API, MySQL `poptracker_farm`, HTTPS API под `/api/device/v1/`. **Не предполагать Laravel внутри Farm.** Существующий PopTracker и его БД, действующий парсер и рабочие задания должны остаться неизменными. Предыдущий локальный путь парсера: `~/Desktop/poptracker/experiments/code/operations/android/collect_in_tiktok.py`; проверить наличие и актуальность, не считать его единственным компонентом.

## 2. Цель и вопросы исследования

Определить, какие сведения об **одном публичном ролике TikTok** Android Agent реально может прочитать через штатные Android API с разрешением пользователя, насколько это сопоставимо с действующим парсером и что понадобится для этапа 3B.2.

Исследовать отдельно:

1. Доступен ли экран TikTok через AccessibilityService на конкретной версии приложения и OPPO.
2. Какие поля можно прочитать: ник автора, текст описания, отображаемые просмотры/лайки/комментарии, дата публикации, ссылка/ID ролика, звук, хештеги. Для каждого поля различать **видно человеку**, **есть в Accessibility tree**, **можно получить надёжно**, **не проверено**.
3. Можно ли однозначно связать наблюдение с `video_id` и существующими `poptracker_videos` / `poptracker_observations` без угадывания идентификаторов.
4. Какие действия выполняет текущий Mac/ADB-парсер и что из них вообще переносимо в Android Agent.
5. Какие ограничения Android, интерфейса, условий использования платформы и разрешений делают сбор нестабильным или недопустимым.

## 3. Обязательные границы

- **Не запускать массовый сбор, обход антибот-защиты, CAPTCHA, лимитов, блокировок или сетевой перехват приложения.** Не извлекать токены, cookies, приватные API или закрытые данные.
- Исследовать только **один заранее выбранный публичный ролик**, при необходимости до трёх ручных повторов на том же ролике. Не собирать чужие приватные сообщения, уведомления, учётные данные, контакты и персональные данные зрителей.
- **Никакого универсального удалённого управления произвольными приложениями:** не добавлять в API команды `tap(x,y)`, `swipe`, `dump_all_windows`, `open_any_app` или выполнение скриптов.
- Сохранять требование явного согласия на AccessibilityService. Не включать разрешения программно.
- Не изменять существующие шесть таблиц PopTracker и не писать исследовательские результаты в рабочую БД роликов.
- Не ломать этапы 1–3A, регистрацию, heartbeat, очередь, локальный outbox, тестовый UI и уже работающие задачи.
- **Не вводить постоянный фоновый режим** и не обещать работу с заблокированным экраном.

## 5. Минимальный исследовательский режим Android Agent

Реализовать **узкий, выключенный по умолчанию диагностический режим** для экрана TikTok. Он включается **вручную на самом телефоне** на ограниченное время и не расширяет серверный API до произвольного управления.

- Проверять точный пакет TikTok, фактическое имя пакета определить на устройстве; не использовать непроверенные константы.
- Для **только текущего окна** собирать структурированные, минимально необходимые сведения о доступных текстовых и семантических узлах: тип, ресурсный ID (если есть), доступный текст, content description, видимость. Ограничить глубину, количество узлов, размер и время снимка.
- По умолчанию **не отправлять сырое дерево UI на VPS**: показывать локальный предпросмотр, сохранять локальный диагностический JSON по явному действию оператора; перед экспортом редактировать чувствительные поля. При отсутствии уверенности в безопасности данных отказаться от экспорта.
- Не выполнять на TikTok нажатий, свайпов, переходов или ввода текста автоматически. Оператор сам открывает публичный ролик.
- Не использовать `MediaProjection`, OCR или захват сетевого трафика в этом этапе. Если Accessibility не раскрывает поле, записать ограничение вместо догадки.
- При чужом пакете, выключенной службе, таймауте или недоступном дереве завершать с типизированной ошибкой без дальнейших действий.
- Добавить диагностическую функцию как отдельный модуль/feature flag, не влияющий на обычные задания.

## 7. Отдельный обязательный блок: исправление протокола результатов

**Не смешивать это исправление с экспериментом TikTok.** Сначала изучить реализацию `lease`, статусов задач, повторов, локального outbox и транзакций на сервере. Подготовить и реализовать совместимое исправление только после тестов и проверки обратной совместимости.

Требования:

1. Разделить **срок получения/начала выполнения**, **дедлайн выполнения** и **доставку уже завершённого результата**. Истечение lease не должно автоматически означать, что результат корректно выполненной попытки необходимо безусловно отбросить.
2. Использовать неизменяемые `task_id`, `attempt_id` и идентификатор/токен назначения (fencing token). Результат принимается **только от авторизованного устройства для известной попытки**.
3. Повторная доставка одного результата должна быть идемпотентной. При одинаковом payload возвращать уже зафиксированный итог; при конфликтующем payload возвращать определённый конфликт без перезаписи.
4. Не допускать, чтобы запоздалый результат **старой попытки** перезаписал итог новой попытки или изменил состояние задачи после переназначения. Сохранять его как диагностическое событие либо отклонять с чётким кодом и документированной семантикой.
5. Для выполненной попытки без переназначения предусмотреть ограниченное окно поздней доставки с явной политикой хранения, проверкой принадлежности и защитой от replay. Конкретные сроки выбрать после изучения текущего кода, а не механически увеличивать 120 секунд.
6. Сохранять готовый результат локально до подтверждения сервера. После рестарта агента не терять outbox.
7. Не менять семантику старых команд незаметно; если меняется протокол, версионировать его и сохранить совместимость с агентом 0.3.1 либо задокументировать контролируемую миграцию.

**Обязательные тесты:** результат через 130 секунд и через 5 минут без переназначения; повтор одинакового результата; конфликтующий повтор; старый результат после новой попытки; отзыв токена; обрыв соединения после серверного commit до получения HTTP-ответа; перезапуск агента с сохранённым outbox. Ожидаемый итог каждой ветки зафиксировать в тестах. Не считать задачу решённой, если проверена только более частая повторная отправка.

## 8. Последовательность выполнения

**Фаза A.** Инвентаризация и baseline; короткий план изменений с рисками.  
**Фаза B.** Исправление late-result semantics с тестами и контролируемым развёртыванием. Повторить тесты этапов 2 и 3A.  
**Фаза C.** Локальный диагностический режим TikTok с ручным открытием одного публичного ролика.  
**Фаза D.** Испытание на OPPO без USB; сохранение минимальных обезличенных артефактов.  
**Фаза E.** Сравнение с существующим парсером и заключение о переносимости.

Перед любыми серверными изменениями сделать резервную копию затрагиваемых файлов и схемы/данных, проверить миграции на тестовой БД. Не применять разрушительные миграции к production. APK обновлять с сохранением регистрации и данных outbox. Если для теста нужен USB только при установке APK, это допустимо; **само испытание связи и диагностики провести без USB**.

## 9. Проверки и критерии приёмки

### Протокол задач
- Все прежние команды `PING`, `GET_DEVICE_STATUS`, `EXECUTE_TEST_TASK`, `UI_TEST_SCENARIO` работают после изменений.
- Повторный отчёт не создаёт дублирующий итог.
- Готовый результат после длительного сетевого обрыва обрабатывается по новой, явно документированной политике; поздний отчёт старой переназначенной попытки не портит состояние новой.
- Регистрация устройства, heartbeat и обработка offline/online сохраняются.

### Исследование TikTok
- На OPPO без USB оператор вручную открыл один публичный ролик.
- Агент с явного локального согласия собрал **только допустимые сведения о текущем окне** или корректно сообщил, почему это невозможно.
- Для каждого целевого поля указано, подтверждена ли доступность, и приложено минимальное свидетельство без секретов.
- Нет автоматических действий внутри TikTok, массового сбора и изменений production-парсера/БД.
- После диагностики собственный UI-тест и три команды этапа 2 по-прежнему работают.

**Не считать приёмкой:** один скриншот без структурированных проверок, неподтверждённые предположения о полях, успешный unit-test вместо проверки физического OPPO, исправление `lease_expired` только уменьшением retry delay.
