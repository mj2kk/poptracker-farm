# PopTracker Farm · Control API v1

Базовый URL на Vuka — `https://7s-01d.online/api/device/v1`. Сервер принимает JSON в UTF-8. Для POST нужен `Content-Type: application/json`, максимальный размер тела 4 КиБ. Все ответы API запрещают кэширование. Клиент не следует перенаправлениям и проверяет сертификат средствами Android.

### Регистрация

`POST /enroll` принимает одноразовый код оператора и версии ПО. Пример структуры запроса с заполнителем:

```json
{"code":"<16 hex characters>","agent_version":"0.1.0","android_version":"13"}
```

Ответ HTTP 201 содержит `device_id` (UUID) и `token` (64 символа hex). Код действует 10 минут. Погашение кода и выпуск токена проходят в одной транзакции. Код регистронезависим, токен следует передавать ровно в полученном виде. Сервер сохраняет только SHA-256 кода и токена. Если ответ потерялся, оператор отзывает выданный UUID и создаёт новую пару.

### Проверка устройства

`GET /me` требует `Authorization: Bearer <device_token>`. Ответ HTTP 200 содержит собственный UUID, `status` и `last_seen_at` в UTC. Сразу после регистрации последнее поле равно `null`. Список устройств доступен оператору через CLI по SSH.

### Heartbeat

`POST /heartbeat` требует тот же Bearer-токен. Пример тела:

```json
{"device_id":"00000000-0000-4000-8000-000000000001","agent_version":"0.1.0","android_version":"13","battery_percent":78,"sent_at":"2026-11-19T15:00:00Z"}
```

`battery_percent` можно пропустить или передать как null. Числовое значение должно быть целым от 0 до 100. Версии имеют длину до 32 символов. Формат `sent_at` — UTC с точностью до секунды. Запись устройства и запись в истории получают одну серверную метку. Ответ HTTP 200 имеет вид `{"received_at":"2026-11-19T15:00:01Z"}`.

Оператор видит `registered` до первого heartbeat, `online` в течение 150 секунд с последнего принятого сообщения, затем `offline`. Следующее принятое сообщение возвращает статус `online`. Статус `revoked` имеет приоритет. История heartbeat хранится семь дней плюс интервал до следующей ежедневной очистки. Во время обрыва агент пропускает недоступные замеры и после восстановления отправляет текущий. Открытый экран удерживает дисплей включённым. При уходе с экрана новые запросы прекращаются, уже отправленный запрос может завершиться.

### Ошибки

Ошибки приложения имеют вид `{"error":"unauthorized"}`. Nginx или внешний прокси могут вернуть собственное тело ошибки. Клиент принимает решение по коду HTTP.

| HTTP | Условие |
|---|---|
| 400 / 415 | Некорректный JSON / неверный тип содержимого |
| 401 | Токен отсутствует, неизвестен или отозван |
| 403 | Неверный, истёкший, использованный код или чужой UUID |
| 404 / 405 | Неизвестный маршрут / метод |
| 413 / 422 | Слишком большое тело / некорректное поле |
| 429 | Ограничение частоты запросов |
| 500 / 502 / 503 | Ошибка приложения или временная недоступность сервера |

После сетевых ошибок heartbeat повторяется с растущей случайной задержкой до 60 секунд. После 429 агент ждёт минуту. Ошибка 401/403 останавливает отправку до повторной регистрации. Регистрация с кодом повторяется оператором вручную.

### Задания · схема 1

Оба маршрута доступны по тому же HTTPS-префиксу, требуют индивидуальный Bearer-токен, JSON и унаследованный лимит тела 4096 байт. Оператор создаёт задания только через CLI. Агент опрашивает очередь при открытом экране через 12 секунд после завершения предыдущего цикла. Heartbeat использует отдельный таймер и рабочий поток.

`POST /tasks/claim` принимает ровно `device_id` и `agent_version`. UUID должен принадлежать владельцу токена. Если очередь пуста или у устройства уже есть действующая попытка, ответ — 204 с пустым телом. Пример структуры ответа 200 с заполнителем секрета:

```json
{"task_id":"00000000-0000-4000-8000-000000000001","attempt_id":"00000000-0000-4000-8000-000000000002","lease_token":"<64 hex characters>","type":"EXECUTE_TEST_TASK","payload":{"duration_ms":1000},"schema_version":1,"lease_expires_at":"2026-11-19T15:02:00Z"}
```

| Тип | payload | result при успехе |
|---|---|---|
| PING | `{}` | `{"pong":true,"executed_at":"2026-11-19T15:00:00Z"}` |
| GET_DEVICE_STATUS | `{}` | manufacturer, model, android_version, api_level, agent_version, опциональные battery_percent и is_charging |
| EXECUTE_TEST_TASK | duration_ms, целое 0–5000 | requested_duration_ms, elapsed_ms и completed=true |

`POST /tasks/{task_id}/result` принимает сохранённый результат конкретной попытки. Для всех типов обязательны оба поля `result` и `error`, одно из которых равно null. Пример запроса:

```json
{"attempt_id":"00000000-0000-4000-8000-000000000002","lease_token":"<64 hex characters>","outcome":"succeeded","result":{"requested_duration_ms":1000,"elapsed_ms":1001,"completed":true},"error":null,"completed_at":"2026-11-19T15:00:01Z"}
```

Пример ответа HTTP 200:

```json
{"task_id":"00000000-0000-4000-8000-000000000001","attempt_id":"00000000-0000-4000-8000-000000000002","outcome":"succeeded","received_at":"2026-11-19T15:00:14Z","result":{"requested_duration_ms":1000,"elapsed_ms":1001,"completed":true},"error":null,"replayed":false}
```

Для `outcome=failed` объект `error` содержит `code` и `message` длиной 1–200 байт. Коды схемы 1 — `UNSUPPORTED_TASK`, `INVALID_PAYLOAD`, `EXECUTION_FAILED`, `EXECUTION_UNKNOWN`. Сервер сверяет типы, обязательные поля и допустимые значения. Lease действует 120 секунд по серверному времени. HTTP 401 означает недействительный токен устройства, 403 — несоответствие устройства или lease, 404 — недоступное задание, 422 — некорректную схему.

После фиксации результата та же попытка с тем же содержимым возвращает первоначальную квитанцию с `replayed=true`, в том числе после срока lease. Изменённое содержимое возвращает 409 `result_conflict`. Первый результат, пришедший после окончания lease, получает 409 `lease_expired`. Сервер фиксирует опоздание, статус попытки становится expired, статус задания — failed. При потере ответа на сам claim устройство ждёт окончания выданного lease. Повторное выполнение требует нового задания оператора.

На сервере транзакция InnoDB сначала блокирует строку аутентифицированного устройства, затем выбранную задачу через SELECT FOR UPDATE. Один телефон получает максимум одну активную попытку. Для разных устройств используются разные строки. READ COMMITTED уменьшает блокировки диапазонов пустых очередей. Секрет попытки хранится на сервере как SHA-256. Срок отсчитывается независимо от heartbeat.

На Android отдельная запись приватных SharedPreferences шифруется AES-GCM с ключом Android Keystore. Агент синхронно сохраняет попытку до выполнения, затем сохраняет полное тело результата и только после этого отправляет его. При перезапуске с известным результатом агент повторяет передачу. Если сохранилась только начатая попытка, агент сообщает EXECUTION_UNKNOWN. Подтверждение или явный терминальный конфликт освобождает очередь. Отклонённый результат и причина сохраняются локально. Это допускает повторы доставки без обещания однократного физического выполнения при любых сбоях.

В APK 0.2.1 при сетевых ошибках готовый результат повторяется с паузой максимум 12 секунд после завершения неудавшегося запроса. Для пустой очереди действует обычный backoff до 60 секунд. HTTP 429 имеет отдельную минутную паузу. Эти интервалы не продлевают lease, а восстановление сети после его окончания всё равно приводит к отказу по первой запоздавшей доставке.

### Этап 3A · UI_TEST_SCENARIO

Версия 0.3.0 передаёт в POST /tasks/claim поле `capabilities: ["OWN_APP_BUTTON_AND_SCROLL_V1"]`. Без этой возможности и версии не ниже 0.3.0 сервер исключает UI-задачи из выборки до сортировки очереди. Старый клиент может получить следующий совместимый тип. Возможность обозначает поддержку схемы клиентом. Состояние системной службы проверяется на телефоне во время исполнения.

Входное поле `payload` содержит ровно `{"scenario":"OWN_APP_BUTTON_AND_SCROLL_V1"}`. В APK допустим только этот фиксированный сценарий на экране Automation Test собственного пакета. Операторские команды, серверная аутентификация, 120-секундный срок попытки и одноразовая выдача сохраняются.

Агент сохраняет отчёт в прежнем зашифрованном журнале до передачи. При успехе `outcome=succeeded`, `error=null`, а `result.status=PASSED`. Структурированный отчёт содержит `schema_version`, `scenario`, `status`, `steps`, `duration_ms` и `error_code`. Сервер проверяет последовательность шагов permission_check → screen_check → reset → counter_zero → button_click → counter_verify → scroll_find_item. Допустимые наблюдения — только «0», «1» и «Test Item 25» на назначенных шагах.

Для диагностируемой ошибки сценария `outcome=failed`, `result.status=FAILED`. В шагах остаются успешный префикс и один последний FAILED. Код из фиксированного списка передаётся также в `error.code`, сообщение имеет вид `Failed at <шаг>`. Общие ошибки исполнителя, включая EXECUTION_UNKNOWN после перезапуска, сохраняют контракт этапа 2 с пустым result. При повторной передаче сервер сравнивает канонический хеш JSON, где порядок полей объектов игнорируется, а порядок шагов сохраняется.

### Протокол доставки результатов v2

Агент 0.3.2 передаёт в claim поле `result_protocol` со значением 2. Ответ добавляет `result_protocol`, `start_budget_ms` и `execution_budget_ms`. Тело результата v2 включает `execution_timing` с целыми `start_ms` и `finish_ms` от отправки запроса claim. Готовый результат принимается ещё 15 минут после дедлайна исполнения текущей попытки. Дедупликация учитывает сохранённые отсчёты. Для попыток v1 действуют прежние поля и сроки. [Состояния, ответы HTTP и границы времени](step-03b1-lease-protocol.md)

### Этап 3B.2. Пакеты тестовых данных

Агент 0.3.3 объявляет capability `COLLECT_TEST_DATA` вместе с `result_protocol: 2` в обычном `POST tasks/claim`. Задание содержит `device_id` и payload вида `{"dataset":"synthetic_videos","record_count":10}`. Сервер принимает целое количество от 10 до 100. Агент отправляет один пакет в поле `result` существующего `POST tasks/{task_id}/result`. Авторизация устройства, lease и сроки доставки описаны в [протоколе v2](step-03b1-lease-protocol.md).

Обязательные поля пакета — `task_id`, `attempt_id`, `device_id`, `batch_id` (UUID в нижнем регистре), `schema_version` (целое 1), `created_at` и массив `records`. Каждая запись содержит `external_id` вида `test_video_001`, `author_id` вида `test_author_001`, `published_at`, `collected_at`, `description` (1–512 байт UTF-8) и четыре целых счётчика `views`, `likes`, `comments`, `shares` от 0 до 4 294 967 295. Формат времени UTC — `YYYY-MM-DDTHH:MM:SSZ`. Массив должен иметь заказанный размер и уникальные external_id. Максимальный размер тела запроса для пакета — 128 КиБ, для обычных сообщений — 4 КиБ.

При успехе `result` в квитанции содержит `batch_id`, `record_count` и `status: "stored"`. Повтор исходного сообщения возвращает прежнюю квитанцию с `replayed: true`. Изменённое сообщение принятой попытки возвращает HTTP 409 с `result_conflict`, занятый другим заданием того же устройства batch_id — HTTP 409 с `batch_conflict`. Неверный владелец вложенного пакета получает 403, чужой ID задания в URL — 404. При неверной схеме возвращается 422, при невалидном JSON — 400, при превышении лимита — 413. Формат ошибки — `{"error":"код"}`. Валидация и сохранение выполняются в одной транзакции.

Оператор может вызвать `GET /api/device/v1/devices` с отдельным Bearer-токеном. Ответ содержит массив `devices` с `device_id`, `display_name`, `status`, `last_seen_at` (UTC или null). Статусы — registered, online, offline и revoked. Без действующего операторского токена ответ 401. Порог online составляет 150 секунд с момента heartbeat. На VPS токен можно передать curl через stdin, чтобы значение не появлялось в списке процессов.

```sh
{ printf 'Authorization: Bearer '; cat /etc/poptracker-farm/operator.token; } |
  curl --fail --silent --show-error --header @- https://7s-01d.online/api/device/v1/devices
```

### Step 4. Выбор исполнителя и мониторинг двух Android

В операторском CLI команда `task:create DEVICE_UUID TYPE [JSON]` создаёт адресное задание. Для общей очереди используется `task:create any TYPE [JSON]`. В `task:list` и `task:show` поле `assignment_mode` принимает значения `targeted` и `any`. У нового задания общей очереди `device_id=null` до успешного claim. Владелец закрепляется за заданием на весь оставшийся срок хранения.

При claim сервер блокирует конкретное авторизованное устройство, проверяет отсутствие активной попытки и сначала ищет совместимую адресную задачу. При свежем heartbeat (до 150 секунд включительно) свободный агент может получить старейшую доступную совместимую задачу общей очереди. Запрос MySQL использует `FOR UPDATE SKIP LOCKED`. Назначение владельца и создание попытки фиксируются в одной транзакции. При обрыве связи действуют сроки протокола v2. Незавершённый пакет закреплён за первоначальным исполнителем.

Операторский `GET /api/device/v1/devices` возвращает прежние поля и дополняет каждую запись:

| Поле | Значение |
| --- | --- |
| `manufacturer`, `model` | Последний успешный GET_DEVICE_STATUS. До первого такого результата возвращается null. |
| `android_version`, `agent_version` | Обновляются при регистрации и heartbeat. |
| `current_task` | null или объект с `task_id`, `attempt_id`, `type`, `assignment_mode`, `phase`. Между окончанием исполнения и концом окна доставки возможна фаза `awaiting_result`. |
| `completed_tasks` | Число успешно завершённых заданий в сохраняемой истории Farm (обычно 30 дней). |
| `last_error` | null или последняя ошибка задания с полями `task_id`, `code`, `at` (UTC). Просроченная попытка видна даже у отключённого телефона. |

Для пакетов Step 4 область уникальности клиентского `batch_id` — одно устройство. В `collection_batches.local_batch_id` хранится ID из JSON, в `collection_batches.batch_id` — ключ хранения. При совпадении ID разных телефонов сервер выделяет второму пакету отдельный ключ хранения. Квитанция содержит исходный клиентский ID. Для чтения строк в SQL выполняйте `JOIN collection_records USING (batch_id)`, для поиска клиентского пакета указывайте `device_id` и `local_batch_id`. Повтор той же попытки возвращает ту же квитанцию. Использование занятого локального ID в другом задании того же устройства даёт 409.

## Обработка сохранённых комментариев на Android

Farm 0.5.0 объявляет возможность `ARCHIVE_COMMENTS_V1` при `tasks/claim` с протоколом 2. Для обработки достаточно оставить Farm открытым с интернетом. Регистрировать обновлённый телефон заново или включать службу специальных возможностей для этой команды не требуется.

После актуального одобрения ИИ Production выдаёт онлайн-телефону партию до 20 комментариев одного видео. В исходном пакете есть `video_id` и массив `comments` с полями `id` и `text`. Размер компактного JSON ограничен 32 КиБ. В ответ Android возвращает тот же видео-ID и упорядоченные пары `id`, `sha256` с SHA-256 точных байтов UTF-8. Долговременный журнал телефона хранит сведения для доставки результата без исходных текстов.

При приёме Vuka сверяет lease, хеши, актуальность одобрения и данные каталога. Изменение исходного текста либо отозванное одобрение блокирует производственное задание. Повтор уже принятого результата возвращает прежнюю квитанцию. Каждая записанная телефоном строка контекста связана с устройством, технической партией и заданием Production. В рабочем режиме тексты остаются в контексте с исходными датами и источником. При отсутствии доступного телефона продолжает работать серверный обработчик.
