# Доставка результатов Farm v2

Протокол действует для попыток, выданных после запроса `tasks/claim` с целым `result_protocol=2`. Он использует прежние HTTPS-маршруты и четыре типа задач. Сервер сохраняет выбранную политику в каждой попытке. Агент 0.3.1 и ранее выданные задания продолжают использовать v1 с прежним 120-секундным сроком. Агент 0.3.2 также доставляет v1-отчёт, сохранённый перед обновлением.

| Срок от выдачи | Правило v2 |
|---|---|
| Начало исполнения — до 20 с включительно | Запас покрывает обычный запрос с 8-секундным connect timeout и 10-секундным read timeout. Клиент замеряет время с отправки claim до фактического старта, включая запись задания на диск. При позднем возврате задания клиент формирует отказ. |
| Завершение — до 120 с включительно | Прежний лимит исполнения сохранён. Самый длинный из действующих сценариев UI имеет собственное ограничение 30 с. Результат выполненной работы содержит начальный и конечный отсчёты монотонных часов клиента. |
| Первая доставка — до 17 минут, верхняя граница исключена | К 120 с добавлены 15 минут на восстановление связи. Это даёт запас для проверенных отключений на 130 и 300 с и ограничивает время, на которое одно потерянное назначение может задержать очередь. |
| Повтор принятого отчёта | Пока хранится попытка, одинаковое тело возвращает исходную квитанцию, включая исходное время приёма. Действует стандартная очистка завершённых задач старше 30 дней. |

Клиент считает время через Android `elapsedRealtime`, начиная до сетевого запроса. Время ожидания сети до выдачи входит в расчёт консервативно. Сервер проверяет диапазоны и порядок сообщённых отсчётов. Доступ к API подтверждает устройство, но сервер не может независимо засвидетельствовать момент физического нажатия на телефоне. Для срока приёма используется UTC сервера. Перевод системных часов телефона не продлевает окно.

## Состояния и конкуренция

1. Выдача создаёт одну попытку с индивидуальным случайным токеном назначения. До сохранения тела результата локальный журнал содержит задание. Перезапуск после возможного выполнения даёт `EXECUTION_UNKNOWN` без повтора действий.
2. Готовый отчёт сохраняется атомарно в зашифрованном журнале приложения. Отправка при восстановлении сети использует сохранённое тело и идентификаторы даже после рестарта. Для неопределённого исполнения или локального отказа до начала допустим ошибочный отчёт с `execution_timing=null`.
3. Между дедлайном исполнения и дедлайном доставки CLI показывает `delivery_phase=awaiting_result`. В БД задача остаётся `leased`. Устройство получает следующую задачу после расчёта по текущей попытке либо после окончательного истечения. Автоматического переназначения в этой версии нет.
4. Сервер блокирует строки авторизованного устройства, задачи и попытки, проверяет принадлежность и хеш токена назначения. Перед первой записью сверяет номер последней попытки. Устаревшее назначение не может изменить более новую попытку. Обработчик истечения также выбирает только последнюю попытку. Тест моделирует историческую и новую попытки одной задачи напрямую в тестовой БД.
5. При первой поздней доставке внутри окна сервер фиксирует исход, начальный и конечный отсчёты и увеличивает `late_results`. При истечении окончательного срока задача получает `failed`, попытка — `expired`. Клиент сохраняет диагностическую копию окончательно отклонённого отчёта. При временных сетевых ошибках или некорректной квитанции готовый отчёт остаётся в очереди отправки.

## Ответы на POST результата

| Условие | HTTP | Пример или смысл |
|---|---|---|
| Первый принятый отчёт | 200 | `{"outcome":"succeeded","replayed":false,…}` |
| Одинаковый повтор, включая повтор после потери ответа | 200 | `{"outcome":"succeeded","replayed":true,…}` с теми же идентификаторами и временем |
| Изменили принятый исход, отсчёты или данные | 409 | `{"error":"result_conflict"}` |
| Есть более новая попытка той же задачи | 409 | `{"error":"attempt_superseded"}` до записи исхода |
| Первая доставка v2 после окна | 409 | `{"error":"delivery_expired"}` |
| Числовые отсчёты успешной работы вышли за бюджет | 409 | `{"error":"execution_window"}` |
| Первая доставка v1 после lease | 409 | `{"error":"lease_expired"}` |
| Отозван Bearer-токен, неверный токен попытки, чужая задача | 401 / 403 / 404 | Запись исхода блокируется |
| Отсутствует обязательный объект времени или структура неверна | 422 | Ошибка формата или версии протокола |

Контрольная сумма включает исход, время завершения, результат и ошибку, а в v2 также отсчёты исполнения. Порядок шагов сохраняется, порядок ключей JSON-объекта не меняет квитанцию. Обработка результата и подтверждение в API разделены границей транзакции: commit предшествует ответу HTTP.

## Выкладка и откат

Сначала применить `server/database/004_result_delivery_up.sql`, затем опубликовать PHP и только после этого установить APK 0.3.2 поверх предыдущего с той же подписью. Миграция добавляет три необязательных столбца в `device_task_attempts`. Старые данные получают NULL.

Для отката оставить совместимый сервер до завершения выданных v2-попыток и отправки локальных отчётов. Следующую сборку клиента с прежней политикой устанавливать с тем же ключом и допустимым versionCode. Возвращать старый обработчик только когда клиенты перестанут запрашивать v2. Сохранять дополнительные столбцы для аудита. Обратная миграция проверена на копии без v2-истории и защищена ограничением от удаления действующих данных v2.
