# PopTracker Farm · Этап 2: Remote Task Execution

**Статус:** техническое задание для Codex  
**Дата:** 19 ноября 2026  
**Зависимости:** `PROJECT.md`, `docs/step-01-report.md`, `docs/setup.md`, фактический исходный код этапа 1.  
**Цель:** сервер назначает Android-агенту безопасные типизированные тестовые задания; агент получает, исполняет и подтверждает результат по HTTPS без USB и без Mac.

## 1. Проверенная исходная точка

По отчёту этапа 1: VPS Vuka, Ubuntu 24.04.2; отдельный PHP 8.3/PDO сервис и MySQL `poptracker_farm` в `/PopTracker Farm`; API размещён на HTTPS-домене `https://7s-01d.online` под `/api/device/v1/`. Существующий PopTracker/Laravel и сборщик TikTok не входят в Farm. Android APK собран для API >= 23, проверен на **OPPO CPH2197 / Android 13 (API 33)**. Зарегистрированный OPPO отправлял heartbeat каждые 60 секунд при открытом приложении, восстанавливался после потери сети без повторной регистрации. В отчёте есть UUID устройства; использовать его из фактического окружения, не прошивать в коде.

**Важно:** сейчас доказана связность одного устройства. Два остальных устройства и фоновая работа не проверены. Не выдавать результат на одном OPPO за проверку трёх устройств.

## 3. Ожидаемое поведение

```text
Оператор (CLI)
   │ создаёт типизированное тестовое задание для device_id
   ▼
Farm Server / MySQL
   │ HTTPS polling: агент запрашивает следующую задачу
   ▼
Android Agent
   │ подтверждает получение/выполнение, выполняет локальную безопасную операцию
   ▼
Farm Server / MySQL
   │ сохраняет результат, время, попытку, итоговый статус
   ▼
Оператор (CLI) видит статус и результат
```

**Выбор транспорта:** продолжить HTTPS polling. Не менять архитектуру на WebSocket. Для MVP агент проверяет задания примерно раз в **10–15 секунд, только пока Activity активна**, с backoff при сетевых ошибках. Существующий heartbeat 60 секунд сохраняется отдельно. Не допускать бесконечного плотного polling.

## 4. Типы задач (строгий allowlist)

Реализовать ровно три типа, с версионированными входными и выходными схемами:

| `type` | Входные данные | Результат | Ограничения |
|---|---|---|---|
| `PING` | `{}` | `pong`, время исполнения агента | Не делать сетевой ping произвольных адресов |
| `GET_DEVICE_STATUS` | `{}` | `manufacturer`, `model`, `android_version`, `api_level`, `agent_version`, `battery_percent` (если доступен), `is_charging` (если доступно) | Не собирать IMEI, Android ID, геолокацию, номера, аккаунты или список приложений |
| `EXECUTE_TEST_TASK` | `{"duration_ms": 1000}` | `requested_duration_ms`, `elapsed_ms`, `completed: true` | Имитировать локальную работу без взаимодействия с TikTok; допустимый диапазон 0–5000 мс; выполнять вне UI-потока |

Не принимать произвольные имена классов, скрипты, URL, пути к файлам или shell-команды в параметрах задачи. Не расширять набор типов без отдельного согласования.

## 5. Состояния, lease и защита от повторов

Рекомендуемая модель статусов: `queued → leased → succeeded | failed`, а также `cancelled` для задач, ещё не взятых в работу. Просроченный lease переводит попытку в `expired`; сама задача может вернуться в `queued` **только по явно заданной политике**.

- Каждая задача имеет серверный UUID `task_id`, целевой `device_id`, `type`, `payload`, `created_at`, `status`, `max_attempts` (для MVP по умолчанию **1**), `expires_at` (необязательно).
- Каждая выдача создаёт `attempt_id` и уникальный непредсказуемый `lease_token` либо эквивалентный защищённый fencing token. Сервер проверяет устройство, задачу, попытку и актуальность lease при приёме результата.
- Начальный lease **120 секунд**. Для тестовых задач максимум 5 секунд достаточно; продление lease в этом этапе необязательно. Не использовать heartbeat устройства как продление lease.
- Получение задачи должно быть **атомарным**: два одновременных запроса не могут получить одну задачу. Использовать транзакцию MySQL и подходящую блокировку строк; обосновать выбор с учётом MySQL 8.
- Повторная отправка того же результата той же попытки должна быть **идемпотентной**: сервер возвращает сохранённый итог, не создаёт новый результат. Конфликтующий повтор с другим содержимым возвращает ошибку.
- Поздний результат после истечения/замены lease не должен менять состояние текущей задачи; вернуть явную ошибку и записать безопасный диагностический факт.
- При потере сети агент сохраняет уже полученное задание и неподтверждённый результат локально, чтобы повторно отправить **тот же** результат после восстановления. Использовать приватное локальное хранилище; если выбран Room/SQLite, объяснить минимальную схему.
- После перезапуска приложения не выполнять повторно задачу, чей исход неизвестен. Для MVP безопаснее пометить такую попытку `execution_unknown` локально и запросить серверное согласование; не обещать exactly-once execution. Доставка заданий в целом **at-least-once**, а для небезопасных действий в будущем потребуются дополнительные гарантии.
- Для `EXECUTE_TEST_TASK` повторение безопасно, но общая модель не должна автоматически разрешать повтор произвольных будущих операций.

## 6. API: предлагаемый контракт v1

Сохранять существующие `/enroll`, `/heartbeat`, `/me`. Реализовать дополнительно (имена можно адаптировать к существующему роутеру, зафиксировав итоговый контракт):

### Агентские маршруты (Bearer device token)

**`POST /api/device/v1/tasks/claim`**  
Тело: `{ "device_id": "UUID", "agent_version": "..." }`. Ответ при наличии задания: HTTP 200 с `{task_id, attempt_id, lease_token, type, payload, schema_version: 1, lease_expires_at}`. При отсутствии: HTTP 204. Сервер проверяет, что device_id соответствует токену. У отозванного устройства запрос отклоняется.

**`POST /api/device/v1/tasks/{task_id}/result`**  
Тело: `{attempt_id, lease_token, outcome: "succeeded"|"failed", result: {...}|null, error: {code, message}|null, completed_at}`. Время на устройстве диагностическое, окончательное время приёма и статус определяет сервер. Ограничить размер JSON и длину сообщений об ошибках. Возвращать итоговую запись и признак повтора; не возвращать секреты.

Опциональный отдельный `ack` не требуется, если claim уже создаёт leased attempt. Если реализация требует `ack`, обосновать его семантику и не допускать промежуточных зависших состояний.

### Операторский интерфейс

Для этапа 2 **достаточно CLI**, аналогичного `bin/farm.php`. Команды (синтаксис уточнить по существующей реализации):

```text
farm.php task:create DEVICE_UUID PING
farm.php task:create DEVICE_UUID GET_DEVICE_STATUS
farm.php task:create DEVICE_UUID EXECUTE_TEST_TASK '{"duration_ms":1000}'
farm.php task:list [DEVICE_UUID]
farm.php task:show TASK_UUID
farm.php task:cancel TASK_UUID
```

CLI должен работать только в локальном операторском контексте с текущей моделью прав. **Не делать публичный endpoint создания задач**, не принимать команды от любого авторизованного устройства для других устройств.

## 7. База данных и миграции

Добавить таблицы либо эквивалентную нормализованную модель:

- `device_tasks`: UUID, `device_id` (FK), `type`, `schema_version`, `payload_json`, `status`, `max_attempts`, `created_at`, `updated_at`, `expires_at`.
- `device_task_attempts`: UUID, `task_id` (FK), `device_id`, номер попытки, `lease_token_hash` (или безопасный эквивалент), `leased_at`, `lease_expires_at`, `completed_at`, `status`, `result_json`, `error_code`, `error_message`, `result_digest`.

Индексы: поиск `queued` по целевому устройству/времени, поиск активной попытки, уникальность номера попытки внутри задачи. Продумать ограничение хранения и максимальный размер JSON. Секрет lease не хранить открытым текстом в БД или логах. Миграции `up`/`down` не должны удалять существующие данные этапа 1. Перед миграцией сделать бэкап Farm DB; проверить откат только на тестовой базе.

## 8. Android: изменения APK

1. Сохранить регистрацию, защищённое хранение device token, статус и heartbeat этапа 1.
2. Добавить независимый polling задач при активном приложении, без блокировки главного потока.
3. Реализовать диспетчер задач с `when(type)` и строгой валидацией `schema_version`, типа и параметров; неизвестный тип → безопасный `failed` с кодом `UNSUPPORTED_TASK`.
4. Не запускать два задания одновременно на одном устройстве в MVP. Пока результат предыдущего не подтверждён, не claim следующую задачу.
5. Сохранять незавершённую попытку и результат для восстановления после обрыва сети. Не сохранять lease token в открытых логах.
6. На экране показать: `device_id`, состояние подключения, время heartbeat, `current_task_id`, тип, статус, последнюю ошибку и последний подтверждённый результат. Добавить кнопку обновления состояния, если это проще.
7. Сохранять минимальные Android permissions этапа 1. Не вводить фоновые сервисы: работа при закрытом/заблокированном экране вне рамок.
8. При серверном отзыве устройства остановить polling и показать необходимость повторной регистрации.

## 9. Безопасность и границы

- HTTPS с системной проверкой сертификата. Не отключать TLS validation.
- Аутентификация устройства по существующему индивидуальному токену; `device_id` из JSON не считается доказательством личности.
- Lease token не заменяет device token; обе проверки обязательны.
- Строгая серверная валидация типа, JSON-схемы, лимитов длительности, длины сообщений, UUID и Content-Type.
- Ограничить частоту claim/result; не допускать утечки секретов в access logs, Logcat, скриншоты и отчёт.
- Только тестовые локальные задачи. Никаких действий с TikTok, обхода ограничений платформы, удалённого произвольного исполнения или доступа к личным данным телефона.
- Отдельно проверить, что неверный или отозванный токен не может получить задачу либо отправить результат.

## 11. Обязательные проверки

### Серверные автоматические тесты

1. Создание каждой из трёх разрешённых задач; отклонение неизвестного типа и невалидных параметров.
2. Устройство A не может claim задачу устройства B.
3. Отозванный/неверный токен получает 401/403 согласно существующему контракту.
4. Два параллельных claim на одну задачу: ровно один победитель.
5. Нет задач → 204.
6. Успешный результат → `succeeded`, данные сохраняются.
7. Повтор идентичного результата не создаёт дубль.
8. Повтор с другим payload → конфликт.
9. Неверный `attempt_id`/lease token → отказ.
10. Просроченный lease → поздний результат не меняет итог.
11. Потеря связи и повторная доставка результата после восстановления.
12. Некорректный JSON, слишком большой payload, неверный Content-Type → отказ.
13. Отмена queued задачи; отменённая задача не выдаётся.
14. Существующие тесты этапа 1 продолжают проходить.

### Android unit tests

- Десериализация задачи, отказ на неизвестную версию/тип.
- `PING`, `GET_DEVICE_STATUS`, `EXECUTE_TEST_TASK` без UI-блокировки.
- Обработка 204, 401, 409, 5xx, таймаутов и backoff.
- Локальный outbox и повторная отправка **того же** результата.
- Запрет второго claim до подтверждения первого.

### Физический E2E на OPPO

1. Обновить APK с сохранением регистрации, убедиться, что heartbeat продолжает работать.
2. Отключить USB; оставить APK открытым.
3. Создать `PING` через CLI, получить `succeeded` и `pong`.
4. Создать `GET_DEVICE_STATUS`, сравнить модель/API level с фактическим OPPO.
5. Создать `EXECUTE_TEST_TASK` на 1000 мс, проверить результат и отсутствие зависания UI.
6. Повторить задачу при временно отключённой сети в момент отправки результата; после восстановления проверить **одну** финальную запись и отсутствие повторного выполнения.
7. Создать задачу для другого `device_id` (тестовая запись/второе зарегистрированное устройство): OPPO не должен её получить.
8. Убедиться, что heartbeat и старый PopTracker не сломаны.

Не отключать сеть во время критичных административных действий; тестировать только безопасные тестовые задания.

## 12. Критерии приёмки

**Минимальный успех этапа 2:** на одном физическом OPPO без USB оператор создаёт все три типа заданий; Android получает их через HTTPS, исполняет и возвращает подтверждённые результаты; после сетевого обрыва не теряется результат; сервер отклоняет чужие и просроченные попытки; тесты этапа 1 не регрессировали.

**Расширенная проверка:** если два других Android доступны, зарегистрировать их и доказать независимое выполнение заданий на трёх устройствах одновременно. Если недоступны, указать `multi-device E2E: pending`, не считать это провалом минимального MVP и не утверждать, что ферма из трёх уже проверена.

**Вне этапа 2:** фоновая работа, TikTok, перенос ADB-парсера, AccessibilityService, управление экраном, скриншоты, панель управления, OTA-обновления, WebSocket, Redis, ML/аналитика трендов.
